# Спецификация требований
## Глоссарий терминов
1. LDAP-аутентификация — механизм проверки подлинности пользователя через LDAP-сервер кафедры.
2. Роль — совокупность прав доступа пользователя в системе.

## Модели требований
### Объекты предметной области
- Гость — пользователь без авторизации.
- Студент — пользователь, имеющий доступ к прохождению назначенных тестов.
- Лектор — пользователь, создающий тесты, управляющий их доступностью и просматривающий результаты студентов.
- Администратор — пользователь с правами управления ролями.
- Тест — сущность, содержащая: название теста, блок сложных и стандартных вопросов и вариантов ответов к ним.
- Вопрос — элемент теста (одиночный выбор или множественный выбор).
- Блок вопросов — группа вопросов, объединённых по сложности (сложные или стандартные).
- Результат теста — итоговая оценка.
- Тестовый файл — текстовый файл специального формата, описывающий структуру теста. 

### Связи между объектами

#### 1. Иерархия пользователей
*   **Гость** не связан с другими объектами, но может инициировать создание объекта **Администратор**, **Студент** или **Лектор** через процесс авторизации.
*   **Администратор** управляет объектом **Студент**, назначая ему роль **Лектор**.

#### 2. Управление тестами
*   **Лектор** является владельцем **Теста**.
*   **Лектор** создает **Тест** на основе загруженного **Тестового файла**.
*   Один **Лектор** может создавать множество **Тестов**.
*   **Тест** состоит из **Блоков вопросов**.
*   **Блок вопросов** включает в себя множество **Вопросов**.
*   **Вопрос** относится к одному **Блоку вопросов** и, следовательно, к одному **Тесту**.

#### 3. Процесс тестирования
*   **Студент** взаимодействует с **Тестом** (проходит его). Связь *многие ко многим* реализуется через попытку прохождения.
*   **Студент** получает **Результат теста** после прохождения конкретного **Теста**.
*   Один **Студент** может иметь множество **Результатов теста** (по одному на каждый пройденный тест).
*   Один **Тест** может иметь множество **Результатов теста** (по одному от каждого студента, который его прошел).

#### 4. Ключевые взаимосвязи объектов
| Объект 1 | Объект 2 | Тип связи | Описание |
|----------|----------|-----------|----------|
| Лектор | Тест | 1 : M | Лектор создает и управляет множеством тестов. |
| Тест | Блок вопросов | 1 : M | Тест содержит несколько блоков вопросов. |
| Блок вопросов | Вопрос | 1 : M | Блок содержит несколько вопросов. |
| Студент | Результат теста | 1 : M | Студент имеет несколько результатов (по разным тестам). |
| Тест | Результат теста | 1 : M | Тест может иметь множество результатов (от разных студентов). |
| Лектор | Тестовый файл | 1 : M | Лектор загружает множество тестовых файлов для создания тестов. |
| Тестовый файл | Тест | 1 : 1 | Один корректный тестовый файл создает один тест в системе. |
| Администратор | Лектор | 1 : M | Администратор может назначать роль лектора множеству пользователей. |

## Модели пользователей системы

### Список пользователей
1. **Гость** — неавторизованный пользователь, имеющий доступ только к странице входа в систему.
2. **Студент** — авторизованный пользователь, имеющий доступ к прохождению тестов, открытых для его учебной группы.
3. **Лектор** — авторизованный пользователь, создающий тесты на основе загружаемых файлов, управляющий доступом к ним для учебных групп и просматривающий результаты студентов.
4. **Администратор** — привилегированный пользователь, управляющий назначением роли лектора другим пользователям системы.

### Права пользователей
#### Гость:
- Просматривать страницу входа в систему.
- Выполнять аутентификацию в системе.

#### Студент:
- Все права гостя .
- Просматривать список тестов, доступных для его учебной группы.
- Начинать прохождение доступного теста.
- Проходить тест, последовательно отвечая на блоки вопросов (сложные, затем базовые).
- Просматривать свои результаты по завершённым тестам.

#### Лектор:
- Все права гостя.
- Создавать тесты путём загрузки файлов специального формата.
- Просматривать список созданных им тестов.
- Удалять созданные им тесты.
- Управлять доступом к своим тестам для учебных групп.
- Просматривать агрегированные результаты студентов по своим тестам.
- Получать ранее загруженный файл теста.

#### Администратор:
- Все права гостя.
- Просматривать список всех лекторов системы.
- Назначать любому пользователю роль лектора.
- Лишать пользователя роли лектора.


## Первичный список требований

Каждое требование имеет приоритет:

- **H** — высокий (критически важно для работы системы)
- **M** — средний (важно, но есть временные обходные пути)
- **L** — низкий (желательно, но можно отложить)

### Функциональные требования


#### 0. Общие

0.1. Все авторизованные пользователи могут завершить сеанс работы (выйти из аккаунта). **(H)**

#### 1. Гость

1.1. Гость имеет доступ только к странице входа в систему. **(H)**

#### 2. Студент

2.1. Студент может авторизоваться в системе через LDAP. **(H)**

2.2. Студент может просматривать список тестов, доступных для его учебной группы. **(H)**

2.3. Студент может начать прохождение доступного теста. **(H)**

2.4. Студент может проходить тест, отвечая на вопросы в установленной последовательности:
- сначала блок сложных вопросов,
- затем, после не успешной сдачи блока сложных вопросов, блок базовых вопросов. **(H)**

2.5. Студент может изменять свои ответы на вопросы до момента завершения соответствующего блока теста. **(H)**

2.6. Система должна автоматически засчитывать все вопросы блока базовых вопросов как правильные, если студент правильно ответил на **все** вопросы блока сложных вопросов. **(H)**

2.7. Студент может пройти каждый тест только один раз. Повторное прохождение того же теста тем же студентом невозможно. **(H)**

2.8. Система должна рассчитывать итоговую оценку за тест на основе результатов прохождения обоих блоков:
- **оценка 5** — 100% правильных ответов;
- **оценка 4** — >= 80% правильных ответов;
- **оценка 3** — >= 50% правильных ответов;
- **оценка 2** — менее 50%;

2.9. Студент может просматривать свои результаты по завершённым тестам. **(H)**

#### 3. Лектор

3.1. Лектор может авторизоваться в системе через LDAP. **(H)**

3.2. Лектор может загружать тестовый файл в специальном формате для создания нового теста. **(H)**

3.3. Система должна выполнять валидацию загружаемого тестового файла:
- проверка структуры файла,
- проверка синтаксиса математических выражений (MathJax).**(M)**

3.4. В случае обнаружения ошибок в тестовом файле система должна отображать лектору список ошибок с указанием их местоположения (строка, тип ошибки). **(M)**

3.5. Лектор может просматривать список созданных им тестов. **(H)**

3.6. Лектор может управлять доступом к своему тесту для учебных групп (открывать доступ). **(H)**

3.7. Лектор может просматривать агрегированные результаты студентов по своим тестам (список студентов и их оценки). **(H)**

3.8. Лектор может скачивать ранее загруженный файл теста. **(M)**

3.9. Лектор может удалять созданные им тесты. **(M)**

3.10. Лектор может загружать изображения. **(M)**

#### 4. Администратор

4.1. Администратор может авторизоваться в системе через LDAP. **(H)**

4.2. Администратор может просматривать список всех лекторов системы. **(M)**

4.3. Администратор может назначать любому пользователю роль лектора. **(M)**

4.4. Администратор может лишать пользователя роли лектора. При лишении роли все тесты, созданные этим лектором, должны быть автоматически удалены. **(M)**

### Нефункциональные требования

#### Безопасность и доступ

5.1. Токен аутентификации пользователя активен в течение 30 дней.

5.2. Токен аутентификации должен деактивироваться при выходе пользователя из аккаунта. 

5.3. Студент имеет доступ только к тестам, открытым для его учебной группы. 

5.4. Студент может просматривать только свои собственные результаты. 

5.5. Лектор имеет доступ только к тестам, созданным им самим. 

5.6. Лектор может просматривать результаты только по своим тестам. 

5.7. Администратор имеет доступ только к функционалу управления ролями и не может просматривать тесты или результаты.

#### Требования к интерфейсу

6.1. Пользовательский интерфейс системы должен быть реализован на русском языке.

6.2. Веб-интерфейс должен корректно отображаться и функционировать в актуальной версии браузера Google Chrome.

#### Требования к производительности

7.1. Система должна поддерживать одновременную работу не менее 20 пользователей без деградации производительности. 

7.2. Время ответа API (за исключением операций загрузки файлов) не должно превышать 5 секунд. 

### Архитектурные требования

8.1. Система должна быть реализована с использованием клиент-серверной архитектуры с разделением на фронтенд и бэкенд. 

8.2. Система должна использовать реляционную базу данных для постоянного хранения информации о пользователях, тестах, результатах и правах доступа. 

8.3. Система должна обеспечивать целостность данных на уровне базы данных. 

8.4. Файлы тестов и изображения должны храниться в выделенном файловом хранилище.

## Функциональная модель системы тестирования

<!-- 0. Общие -->
**Сценарий 0.1: Выход из аккаунта (ФТ №0.1)**
1. **Предусловие:** Пользователь (Студент, Лектор или Администратор) авторизован в системе.
2. **Действие:** Пользователь нажимает кнопку "Выйти" (или соответствующий элемент интерфейса).
3. **Результат:** Система завершает сессию пользователя, деактивирует токен аутентификации и перенаправляет пользователя на страницу входа.
4. **Постусловие:** При попытке перейти по защищенному URL пользователь перенаправляется на страницу входа.

<!-- 1. Гость -->
**Сценарий 1.1: Доступ гостя к системе (ФТ №1.1)**
1. **Предусловие:** Пользователь не авторизован (Гость).
2. **Действие:** Гость открывает главный URL приложения.
3. **Результат:** Система отображает только страницу входа с полями для ввода логина и пароля. Гость не видит никаких других разделов (список тестов, результаты, администрирование) и не может к ним перейти, даже вручную вводя адрес в строке браузера.

<!-- 2. Студент -->
**Сценарий 2.1: Авторизация студента (ФТ №2.1)**
1. **Предусловие:** Гость находится на странице входа.
2. **Действие:** Гость вводит корректные данные (логин/пароль) учетной записи студента из LDAP и нажимает "Войти".
3. **Результат:** Система перенаправляет пользователя в интерфейс студента.

**Сценарий 2.2: Просмотр доступных тестов (ФТ №2.2)**
1. **Предусловие:** Студент авторизован и принадлежит к учебной группе, для которой лектор открыл тест.
2. **Действие:** Студент переходит в раздел "Тесты" (или на главную страницу студента).
3. **Результат:** Система отображает список тестов, доступных для группы студента. Тесты, которые студент уже прошел, помечены как "Завершены" и неактивны для повторного прохождения.

**Сценарий 2.3: Начало прохождения теста (ФТ №2.3)**
1. **Предусловие:** Студент находится в списке доступных тестов.
2. **Действие:** Студент выбирает тест, который еще не проходил, и нажимает кнопку "Начать тест".
3. **Результат:** Система открывает первую страницу теста (блок сложных вопросов).

**Сценарий 2.4: Прохождение теста (ФТ №2.4)**
1. **Предусловие:** Студент начал прохождение теста, в котором есть оба блока.
2. **Действие:** Студент отвечает на все вопросы в блоке сложных вопросов и завершает блок (нажимает "Далее").
    - *Если сложные вопросы отвечены неверно*, система открывает блок базовых вопросов.
    - *Если сложные вопросы отвечены верно*, блок базовых вопросов пропускается (согласно ФТ №2.6).
3. **Результат:** Студент последовательно проходит блоки, предусмотренные логикой теста.

**Сценарий 2.5: Изменение ответов в блоке (ФТ №2.5)**
1. **Предусловие:** Студент проходит блок вопросов (например, сложных).
2. **Действие:** Студент выбирает ответ на вопрос, затем, до нажатия кнопки завершения блока ("Далее"), меняет свой ответ на другой.
3. **Результат:** Система корректно фиксирует новый выбранный ответ. При завершении блока система учитывает именно последний выбранный вариант.

**Сценарий 2.6: Автоматическое зачисление базовых вопросов (ФТ №2.6)**
1. **Предусловие:** Студент проходит тест, содержащий блок сложных и блок базовых вопросов.
2. **Действие:**
    - Студент правильно отвечает на **все** вопросы блока сложных вопросов.
    - Студент завершает блок сложных вопросов.
3. **Результат:** Система не отображает блок базовых вопросов, сразу переходит к экрану завершения теста и фиксирует 100% правильных ответов за весь тест (или выставляет оценку "5", так как сложные вопросы отвечены верно). В результатах теста все базовые вопросы отмечены как правильные.

**Сценарий 2.7: Однократное прохождение теста (ФТ №2.7)**
1. **Предусловие:** Студент завершил прохождение теста (сценарий 2.4 или 2.6).
2. **Действие:** Студент возвращается в список тестов и пытается нажать кнопку "Начать тест" для того же теста.
3. **Результат:** Кнопка "Начать тест" неактивна или отсутствует. Система не позволяет создать вторую попытку, отображая сообщение о том, что тест уже пройден.

**Сценарий 2.8: Расчет итоговой оценки (ФТ №2.8)**
1. **Предусловие:** Студент завершил тест.
2. **Действие:** Система подсчитывает процент правильных ответов.
3. **Результат:** Система сохраняет и отображает итоговую оценку в строгом соответствии с правилами:
    - 100% → "5"
    - 80-99% → "4"
    - 50-79% → "3"
    - < 50% → "2"

**Сценарий 2.9: Просмотр своих результатов (ФТ №2.9)**
1. **Предусловие:** У студента есть хотя бы один завершенный тест.
2. **Действие:** Студент переходит в раздел "Результаты" или "Мои результаты".
3. **Результат:** Система отображает список пройденных студентом тестов с указанием даты прохождения и итоговой оценки. Студент может выбрать конкретный тест для просмотра детальной статистики.

<!-- 3. Лектор -->
**Сценарий 3.1: Авторизация лектора (ФТ №3.1)**
1. **Предусловие:** Гость находится на странице входа.
2. **Действие:** Гость вводит корректные данные (логин/пароль) учетной записи лектора из LDAP и нажимает "Войти".
3. **Результат:** Система перенаправляет пользователя в интерфейс лектора.

**Сценарий 3.2: Загрузка тестового файла (ФТ №3.2)**
1. **Предусловие:** Лектор авторизован и находится в интерфейсе создания теста.
2. **Действие:** Лектор нажимает кнопку "Загрузить тест", выбирает корректный файл на своем компьютере и подтверждает загрузку.
3. **Результат:** Файл загружается на сервер, и система инициирует процесс валидации (ФТ №3.3).

**Сценарий 3.3 и 3.4: Валидация файла и обработка ошибок (ФТ №3.3, 3.4)**
1. **Предусловие:** Лектор загрузил тестовый файл (сценарий 3.2).
2. **Действие:** Система выполняет проверку.
    - *Кейс А (успех):* Файл корректен.
    - *Кейс Б (ошибка):* В файле есть ошибка (например, пропущена скобка в MathJax, неверный заголовок блока).
3. **Результат:**
    - *Кейс А:* Тест успешно создается и сохраняется в системе. Лектор видит сообщение об успехе.
    - *Кейс Б:* Тест **не создается**. Система отображает лектору понятное сообщение об ошибке с указанием: "Ошибка в строке 15: непарная скобка в математическом выражении".

**Сценарий 3.5: Просмотр списка своих тестов (ФТ №3.5)**
1. **Предусловие:** Лектор авторизован.
2. **Действие:** Лектор переходит в раздел "Мои тесты".
3. **Результат:** Система отображает список всех тестов, созданных данным лектором. В списке видны названия тестов, дата создания и статус доступа.

**Сценарий 3.6: Управление доступом к тесту (ФТ №3.6)**
1. **Предусловие:** Лектор находится в списке своих тестов.
2. **Действие:** Лектор выбирает тест, нажимает кнопку "Управление доступом", вводит название учебной группы и сохраняет изменения.
3. **Результат:** Система связывает выбранный тест с указанной группой. Студенты этой группы теперь видят тест в списке доступных (ФТ №2.2).

**Сценарий 3.7: Просмотр результатов студентов (ФТ №3.7)**
1. **Предусловие:** Лектор создал тест, и студенты его прошли.
2. **Действие:** Лектор в разделе "Мои тесты" выбирает нужный тест и нажимает "Результаты" (или "Статистика").
3. **Результат:** Система отображает сводную таблицу: список студентов, прошедших тест, и их итоговые оценки.

**Сценарий 3.8: Скачивание тестового файла (ФТ №3.8)**
1. **Предусловие:** У лектора есть хотя бы один созданный тест.
2. **Действие:** В списке "Мои тесты" лектор нажимает иконку "Скачать файл теста" рядом с нужным тестом.
3. **Результат:** Браузер загружает на компьютер лектора файл, содержимое которого идентично тому, что было загружено при создании теста.

**Сценарий 3.9: Удаление теста (ФТ №3.9)**
1. **Предусловие:** Лектор находится в списке своих тестов.
2. **Действие:** Лектор нажимает кнопку "Удалить" рядом с тестом и подтверждает действие во всплывающем окне.
3. **Результат:** Тест и все связанные с ним данные (результаты студентов, файл) полностью удаляются из системы. Тест исчезает из списка лектора и становится недоступен студентам.

**Сценарий 3.10: Загрузка изображений (ФТ №3.10)**
1. **Предусловие:** Лектор находится в интерфейсе создания/редактирования теста.
2. **Действие:** Лектор нажимает кнопку "Загрузить изображение", выбирает файл изображения и подтверждает загрузку.
3. **Результат:** Изображение загружается на сервер, и система генерирует ссылку для вставки в Markdown-файл, которую можно скопировать.

# Высокоуровневая архитектура
## Frontend

### Модуль авторизации

* Формы входа через LDAP.
* Обработка ошибок при аутентификации.
* Хранение JWT-токенов.
* Редирект на главную страницу после успешного входа.

### Модуль тестов

* Просмотр списка доступных тестов.
* Фильтрация и поиск тестов.
* Возможность приостановки и продолжения прохождения теста.

### Модуль результатов

* Отображение результатов завершённых попыток.
* Детальная статистика по каждому тесту.

### Модуль лектора

* Создание, редактирование тестов.
* Публикация/скрытие тестов.
* Управление доступом к тесту для учебных групп.
* Загрузка изображений и тестовых файлов.

### Модуль администратора

* Интерфейс назначения и лишения ролей пользователям.

### Общий UI-компонентный слой

* Кнопки, формы, уведомления, модальные окна.
* Таблицы и списки, повторно используемые во всех модулях.

## Backend

Система построена по трёхуровневой архитектуре: **Handler → Service → Repository**.

### 1. Handler (API/HTTP)

* Приём и валидация HTTP-запросов от фронтенда.
* Вызов сервисного уровня и формирование JSON-ответов.
* Обработка ошибок и возврат корректных кодов статусов.

### 2. Service (бизнес-логика)

* Авторизация и аутентификация через LDAP.
* Управление правами доступа (Студент, Лектор, Администратор).
* Логика прохождения тестов (блоки, подсчёт оценок, однократное прохождение).
* Валидация и парсинг тестовых файлов.
* Управление тестами, вопросами, блоками и результатами.
* Проверка бизнес-правил и условий системы.

### 3. Repository (доступ к данным)

* CRUD операции с реляционной базой данных PostgreSQL.
* Обеспечение целостности данных и транзакций.
* Методы выборки с учётом прав доступа (тесты для группы, результаты по тестам).

### Основные модули Backend

* **LDAP** — аутентификация и получение информации о пользователях.
* **Валидация тестовых файлов** — проверка структуры и синтаксиса.
* **Парсер тестовых файлов** — преобразование файлов в объекты тестов, блоков и вопросов.
* **Прохождение тестов** — логика блоков, фиксация ответов, подсчёт результатов, приостановка/возобновление.

### База данных

* Хранение пользователей, ролей, тестов, вопросов, блоков и результатов.
* Поддержка ограничений целостности (foreign key, unique, not null).

## Критерии аттестации системы

Перед сдачей работы заказчику необходимо выполнить следующие подготовительные шаги:

### Проверка доступа и безопасности

* Проверить работу авторизации через LDAP для студентов, лекторов и администратора.
* Проверить корректность работы логина/пароля для администратора.
* Убедиться в корректной выдаче и деактивации JWT-токенов при выходе из аккаунта.
* Проверить разграничение прав доступа между гостями, студентами, лекторами и администраторами.

### Тестирование функционала для гостей

* Проверить доступ к странице входа в систему.
* Убедиться, что гость не может просматривать список тестов, результаты или административные разделы.

### Тестирование функционала студентов

* Проверить авторизацию через LDAP.
* Убедиться, что студент видит только доступные для него тесты.
* Протестировать прохождение теста:

  * Открытие вопросов и блоков теста.
  * Выбор и изменение ответов до завершения блока.
  * Последовательное прохождение блоков (сложные → базовые).
  * Автоматическое засчитывание блоков базовых вопросов при правильных ответах на все сложные вопросы.
* Проверить расчёт итоговой оценки в соответствии с правилами:
  * 100% правильных → оценка "5"
  * > = 80% → оценка "4"
  * > = 50% → оценка "3"
  * < 50% → оценка "2"
* Проверить, что студент может пройти каждый тест только один раз.

### Тестирование функционала лекторов
* Проверить авторизацию через LDAP.
* Проверить загрузку тестового файла и валидацию структуры и синтаксиса (MathJax).
* Проверить отображение ошибок с указанием строки и типа ошибки при некорректном файле.
* Протестировать создание, редактирование, удаление тестов.
* Проверить управление доступом к тестам для учебных групп.
* Проверить просмотр агрегированных результатов студентов по своим тестам.
* Проверить скачивание ранее загруженного тестового файла.
* Проверить загрузку изображений и корректное отображение в тесте.

### Тестирование функционала администратора

* Проверить доступ к списку пользователей и управление ролями.
* Проверить назначение и лишение роли лектора.
* Проверить, что при лишении роли лектора все тесты и результаты этого лектора удаляются.
* Убедиться, что администратор не имеет доступа к тестам и результатам студентов.

### Проверка ограничений системы

* Проверить ограничения на загрузку тестовых файлов (структура, формат, синтаксис).
* Проверить корректность работы одновременных сессий (не менее 20 пользователей).
* Проверить ограничения на однократное прохождение теста студентом.

### Критерии успешной сдачи

Система считается успешно сданной и аттестованной, если:

* Все функциональные требования реализованы и выполняются корректно.
* Разграничение прав доступа работает правильно для всех ролей.
* Автоматическая оценка тестов и подсчёт результатов выполняются корректно.
* Система корректно обрабатывает ограничения на тесты и попытки.
* Ошибки и уведомления отображаются своевременно и содержат корректную информацию.
* Не выявлено критических ошибок, влияющих на работу системы.

### Сценарий аттестации системы

1. Пользователь запускает веб-приложение.
2. **Гость** видит страницу входа:
   * Попытка доступа к списку тестов блокируется.
3. Гость авторизуется как **студент** через LDAP:
   * Система отображает список доступных тестов.
   * Студент выбирает тест и начинает прохождение:
     * Отвечает на блок сложных вопросов.
     * При правильных ответах на все сложные вопросы система автоматически засчитывает блок базовых вопросов.
     * Студент завершает тест, система рассчитывает результат и отображает статистику.
   * Студент приостанавливает тест и закрывает браузер.
     * При повторном входе студент может продолжить тест с того же места.
4. **Лектор** авторизуется через LDAP:
   * Загружает новый тестовый файл.
   * Система проверяет структуру теста и отображает ошибки, если они есть.
   * Лектор редактирует вопросы и публикует тест.
5. **Администратор** входит в систему:
   * Просматривает список пользователей.
   * Назначает роль лектора новому пользователю.
